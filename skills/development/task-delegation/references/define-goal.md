# Define goal

Follow the main skill's [goal and skill selection](../SKILL.md#goal-and-skill-selection) rule. Derive the outcome, target, scope, and acceptance evidence from the request and known context. Prefer an existing validator or direct observation over an invented metric.

- Bug: reproduce the failure and verify the requested behavior after repair.
- Research: identify the decision, source boundary, and evidence needed to support it.
- Delivery: identify the required destination state, checks, and authority.
- Performance: agree on the meaningful metric and measurement method when they are not already established.

## Ask and decide

Ask focused questions about consequential preferences, scope and tradeoffs; give a recommendation with each. Continue independent work while awaiting answers. Wait for essential decisions; for optional preferences, allow a reasonable response opportunity, then state a reversible assumption and proceed. Make routine choices directly. A clear task needs no ceremonial rewrite or extra confirmation. Use existing authorization and the delivery harness; add no permission or merge reconfirmation gates. Actual runtime and repository restrictions still apply.

## Track lightly

Use the lightest tracking that will remain useful, and reuse a matching active goal or task record when one exists:

- **Conversation:** small, single-session work.
- **Linear or the project's equivalent:** prioritization, shared ownership, cross-session coordination or a committed follow-up; reuse an existing issue.
- **Plan file:** durable local steps using the repository's convention when no suitable tracker exists.
- **OpenSpec:** business rules or product acceptance contracts when available; link the execution record to the spec.

Search before creating records. Keep one authoritative requirements source and at most one execution record; link rather than duplicate. Record acceptance evidence there, and mark completion only when that evidence establishes the requested outcome. Report created records only after success; use an allowed fallback if tools are unavailable.
